# Gaps left by the plugin split
Generated by `tools/split-plugins`. Everything under `plugins/` builds without
the others and nothing in `server` or `client` can see a plugin. These are the places where that
could not be achieved by moving files, and what was done instead.

## Plugin classes that stay in core
None: core code uses no plugin class.

## Classes assigned to a plugin from another package
These keep their package names, so scripts and serialized data are unaffected, but ship in the plugin's jars
(`model.OWNERSHIP_OVERRIDES`).

- `com.mirth.connect.connectors.ConnectorTests` -> `js:server`
- `com.mirth.connect.model.converters.DICOMConverter` -> `dicom:common`
- `com.mirth.connect.server.attachments.dicom.DICOMAttachmentHandler` -> `dicom:server`
- `com.mirth.connect.server.attachments.dicom.DICOMAttachmentHandlerProvider` -> `dicom:server`
- `com.mirth.connect.server.userutil.DICOMUtil` -> `dicom:server`
- `com.mirth.connect.server.userutil.DatabaseConnectionFactory` -> `jdbc:server`
- `com.mirth.connect.server.userutil.HTTPUtil` -> `http:server`
- `com.mirth.connect.server.util.DICOMMessageUtil` -> `dicom:server`
- `com.mirth.connect.userutil.HTTPUtilTest` -> `http:server`

## Promoted to the shared jar
A shared class must not depend on server-only classes of its plugin; these were moved to `common`.

- `com.mirth.connect.plugins.datatypes.delimited.DelimitedBatchAdaptor` (used by shared class DelimitedBatchAdaptorFactory.java)

## Plugin libraries core compiles against
Core classes import these third-party libraries, so `server` compiles against them (`compileOnly`) although they are
shipped by the plugin. Vendored jars of that kind stay in `server/lib/extensions` and the plugin packages them from there.

- none

## Plugins that depend on each other
Gradle cannot build a cycle, so these tiers compile together in the first one's project. Each still has its
own directory, tests and jar; the second project only packages and tests its part.

- `http:server`, `httpauth:server` (compiled in `:plugins:http:server`)

## Core tests that use plugins
Core tests exercise plugin classes, either directly or through core code that names them (migrations, default
configuration, XStream documents), so `server` has a test-scope dependency on these. Main code is unaffected.
A test whose subject is a plugin class lives with the plugin (`model.OWNERSHIP_OVERRIDES`). These stay because the
subject is core and the plugin class is its input: the script builders need real step and rule types, the JSON and
XML serializers need real connector properties, and the shared fixtures (`TestUtils`, `TestServer`) wire up a VM channel.

## Other structural changes
- `server/setup` and `server/dist` are now `distribution/setup` and `distribution/dist`; `createDerbyDb` and
  `devLauncher` moved to `:distribution`. The signing keystore and manifest moved with them.
- The core jars are built into `server/build/libs` and copied into `setup/` by `:distribution`.
- A plugin tier compiles against all of `server`; nothing stops a `common` class from reaching a server-only
  core class, only that it would fail to load in the Administrator.
- Third-party libraries still come from the shared `server-main`/`client-main` bundles; only the libraries that
  were already per extension (`server-extensions`) moved into the owning plugin.
- Plugins ship their own user API sources (`extensions/<name>/src/<name>-userutil-sources.jar`, registered in their
  descriptor); the javadoc for those packages is built by `:distribution` from `plugins/<name>`.
